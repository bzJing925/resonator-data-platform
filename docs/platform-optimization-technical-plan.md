# 数据平台体验优化：技术归并与实施计划

日期：2026-10-09。状态：技术归并初稿，未开始实现。后续细化与执行顺序见 [Luna执行入口](plans/platform-optimization-luna-execution.md)，字段及已定方案以新版任务书为准。

本计划承接八项使用体验建议，供下一轮 Sol 扩展为 Luna 可逐条执行的任务书。本轮不调用其他模型、不修改业务实现。

## 1. 当前实现与约束

- 前端：React 18、TypeScript、Vite、Plotly；桌面壳为 Electron；静态网页版使用 DuckDB-WASM、Arrow、ONNX Runtime Web。
- 后端：Python 3.12、FastAPI、Pydantic、SQLAlchemy；服务器任务使用 Celery/Redis，桌面任务使用本地队列。
- 数据库：已有 PostgreSQL 与 SQLite 两条路径；SQLite 桌面初始化包含手工升级，不能假设新增 Alembic 迁移就覆盖桌面升级。
- 分析工作区已有 dataset/commands/history/selectors，继续复用 reducer 与命令系统。PageStateContext 已用 localStorage 保存部分页面状态，但 AnalysisWorkspaceProvider 的完整数据表和历史没有接入这套存储。
- 取消上传任务会清理批次和文件；取消重处理任务已经不清理既有数据。后续重点是统一交互语义、终止确认及防止旧 worker 继续写入。
- CSV 后端已有流式读取；XLSX 当前在请求内构建，先将查询结果全部读入内存；共享导出查询受 200,000 行上限约束。不能把当前接口直接称为“全量异步导出”。
- 工作区 dataset.revision、同步 SyncRevision、未来处理结果版本含义不同，不得混用。
- 当前工作树已有大量修改及未跟踪的 replication v2 文件；本计划依据工作区现状，不代表这些实现已发布或通过验证。实施前先记录基线并确认在途同步改动，不能覆盖或重做。

主要依据：frontend/src/features/analysis/、frontend/src/contexts/PageStateContext.jsx、frontend/src/api/static/、backend/app/api/tasks.py、backend/app/services/export_query.py、backend/app/services/replica_service.py、backend/app/workers/dispatch.py、backend/app/desktop_setup.py。

## 2. 技术重叠归并

| 共用能力 | 覆盖体验需求 | 共用数据与组件 |
| --- | --- | --- |
| A 任务与入库质量记录 | 预检查、入库验收单、批量进度、失败重试、首页待办 | ProcessingRun、ProcessingItem、QualityIssue、任务事件和汇总 |
| B 数据身份、版本和生命周期 | 停止与删除分离、重算保护、回收站、同步冲突、历史分析复现 | SourceRef、结果版本、删除标记、操作记录 |
| C 分析项目存储 | 自动保存、模板、快照、最近打开、报告 | AnalysisProject、AnalysisSpec、DatasetSnapshot、存储适配器 |
| D 查询口径和结果说明 | 数据范围提示、完整导出、批次对比、报告统计 | QuerySpec、ResultManifest、字段元数据、质量规则 |
| E 同步与能力展示 | 同步状态、统一设置、首页异常入口、模式差异 | Capabilities、SyncStatus、状态徽标和恢复动作 |

报告是 C+D 的输出，首页是 A+C+E 的汇总，批次对比是 D 的专用分析模板；不分别建立第二套查询、统计和状态系统。

避免过度归并：上传与导出复用状态协议及调度适配器，不把导出强塞进依赖 batch_no 的 UploadTask；业务快照复用现有快照序列化能力，但不把“同步缓存”当作不可变分析快照。

## 3. 技术决策

### 3.1 保持现有技术栈

不新增微服务、消息系统、全局状态库或 UI 库。前端继续 React reducer/context、自定义 CSS 和 Plotly；服务层承接新增业务规则，core 保持算法纯函数。常量与容量限制进入配置。

服务器和桌面都通过现有 dispatch 层分发任务，业务计算与存储逻辑保持共用。原生 SQLite 服务器同样必须覆盖，不以“服务器”推断数据库一定为 PostgreSQL。

### 3.2 先固定五类契约

1. SourceRef：origin_id、source_batch_id、source_device_key、source_revision。跨端不能仅依靠本地数据库整数 id；重处理换行 id 后仍应能追溯器件。
2. ProcessingRun：task_id、run_id、attempt、配置摘要、算法版本、输入摘要、开始/结束时间、状态；ProcessingItem 记录可重试单元、结果和错误码。
3. AnalysisSpec：schema_version、筛选、字段、分组、图表、排除规则、单位、质量规则版本；模板保存规格，快照保存实际数据及来源。
4. ResultManifest：查询规格、来源版本、匹配总数或未知值、返回数、是否截断/采样、采样方式、局部编辑/排除数、生成时间。未知总数不能伪装成零或精确总数。
5. SyncStatus：目标端、已确认版本、待同步版本、最后成功时间、错误码、可重试性。与处理状态分离。

Python 使用 Pydantic，前端使用 TypeScript 类型及契约样例测试；本期不引入新的代码生成流水线。

### 3.3 分析项目存储

- 第一版统一采用 IndexedDB 保存客户端项目，localStorage 只保留轻量偏好；三种前端模式共享同一 ProjectStore 接口。
- 保存 manifest、图表配置和分块数据，禁止每次编辑序列化全部数据和无限撤销历史；恢复已保存结果，撤销栈默认仅在当前会话有效，并在 UI 明示。
- 草稿写入新版本，提交完成标记后再切换当前指针；保存失败保留上一个完整版本，显示失败原因。多窗口采用项目版本检查，禁止静默覆盖。
- 命名项目支持版本化 JSON 文件导入/导出作为显式备份；第一版不把原始曲线文件打包进去，也不宣称 IndexedDB 能抵抗用户清除站点数据。
- 项目共享第一版采用导出文件；多人在线编辑、权限和冲突合并单独立项。

### 3.4 版本与数据安全

- 复用现有副本身份、SyncRevision 与 TableReceipt。当前版本触发器主要覆盖 SQLite；先补齐 PostgreSQL 与批量写入的版本推进测试，再对外承诺一致行为。
- 第一阶段不保存所有历史器件副本。重算写入 staging 结果和独立文件目录，成功校验后以短事务切换活动结果；取消/失败不发布 staging。
- 活动结果切换由 run_id 与预期来源版本保护；旧任务即使恢复运行也不能覆盖新结果。现有批量写入服务内部 commit，必须先拆出明确事务边界，不能只在外层加 transaction。
- 取消状态建议为 pending/running → cancel_requested → cancelled，终态由 worker 确认或恢复巡检核实；完成与取消竞争通过条件更新处理。仅标记 cancelled 不等于 worker 已停止。
- 回收站先软删除，所有查询、统计、导出、同步目录一致排除。文件延期清理，清理动作可重试。客户端移除副本还需保存本地忽略记录，避免下次同步自动重新下载。
- 同步协议显式表达删除/恢复版本；临时不可见、处理中、请求失败不能解释为删除。旧客户端协议能力不足时禁用跨端破坏性操作。

### 3.5 查询、导出和报告

- QuerySpec 是查询、对比、导出的共用入口；服务端 SQLAlchemy 与静态 DuckDB 保持实现分离，使用相同测试数据核对结果。
- 当前工作区导出保留局部修改；全筛选导出从数据源重查，不继承图表行数上限，也不包含未提交的本地修改。
- 大量导出使用独立 ExportJob 和现有执行器适配层；分块读取、write-only XLSX、超过单工作表容量自动拆表。输出只在完整成功后可下载，取消后清理临时文件。
- 导出绑定固定来源版本，开始/结束核验版本；变更时显式失败重试，禁止交付混合版本结果。静态版只承诺已发布快照中的全量，达到内存预算时明确拒绝或分批处理。
- CSV 配套 manifest.json，XLSX 增加说明页；报告消费同一个 ResultManifest。首版报告为自包含 HTML 与打印样式，支持浏览器打印 PDF，不先新增服务端 PDF 引擎。

## 4. 可执行工作包

每包独立提交，按下列依赖实施；这是技术级工作包，下一轮再展开到逐文件、逐函数步骤。

### T0 基线与模式矩阵

- 记录 git 状态、现有测试结果、数据库启动/升级路径、三端能力和同步协议版本；在不改动现有工作的前提下明确实施基线。
- 形成固定验收数据：正常文件、重复文件、坏文件、缺校准件、部分失败、同名跨来源批次、超过当前导出上限的数据集。
- 交付：模式矩阵、基线失败清单和测试夹具。依赖：无。
- 完成条件：每项既有失败与新增回归可区分；不以完整测试全绿作为不可达的起点，但不得掩盖既有失败。

### T1 共用契约与兼容升级

- 新增 processing/analysis/result_manifest 契约，扩展分析 dataset 来源元数据；建立任务状态转换函数。
- 新增 run/item/issue 所需存储，升级服务器迁移及桌面 SQLite 初始化路径；仅做增量兼容，不重命名大表。
- 为已存在数据允许来源/算法版本未知，不伪造历史版本。
- 验收：旧数据库升级后可读；重复启动不重复迁移；Pydantic/TS 契约样例一致。
- 依赖：T0。主要落点：backend/app/models、schemas、alembic、desktop_setup.py，frontend/src/types 与 features/analysis/model。

### T2 上传预检查与入库验收

- 拆为浏览器轻量检查和上传后、计算前的服务端深检查；大 ZIP 不在浏览器解压，也不重复上传。
- 各 worker 在共用记录接口写入文件/端口处理结果与错误码；汇总从记录产生，不解析进度文案。
- 明确计数单位：文件、解析器件、器件处理尝试分开，校准文件和忽略文件单独统计；终态计数可对账。
- Upload/FloatingUploadProgress/TaskDetail 展示同一批量列表；提供验收摘要和问题 CSV。
- 验收：部分失败不会显示为全部成功；重新打开任务可恢复完整摘要；桌面和服务器得到同样计数。
- 依赖：T1。落点：upload_service、workers、Upload.tsx、TaskDetail.tsx、UploadProgressContext。

### T3 安全停止、重算发布和失败重试

- 实现 cancel_requested 和 worker 安全检查点；进度更新和发布都校验 run_id，防止终态被迟到事件覆盖。
- 改造写入服务事务边界与 staging 发布；完成新旧结果切换失败恢复，先覆盖 recompute，再覆盖 reextract/redeembed/remap。
- 失败项重试使用稳定来源键和幂等标识；重试缺校准依赖的器件时重新验证其依赖，不盲目按单文件重跑。
- 验收：取消与完成竞争、重复取消、任务崩溃、重复重试均不误删原始输入，不重复入库，不破坏上一版结果；旧任务恢复后不能写入活动结果。
- 依赖：T1、T2。落点：api/tasks、workers/cancel、dispatch/local_queue、device_ingest 和处理服务。

### T4 回收站与同步删除语义

- 新增删除影响预览、软删除、恢复、到期清理；区分仅移除本地副本与服务器删除。
- 将有效批次过滤集中在服务层并覆盖 query/aggregate/stats/export/snapshot/replication；同步增加显式删除与恢复标记。
- 第一版到期清理在服务器定时任务和桌面启动维护中执行，复用相同服务；配置保留期，原始输入与被引用快照的清理规则分别明确。
- 验收：软删除后所有业务入口不可见；恢复后数量和文件可用；离线客户端重连正确收敛；旧客户端不得触发错误清理；本地移除后不会自动回流。
- 依赖：T3；必须协调当前在途 replication v2 改动。

### T5 分析项目、模板和恢复

- 实现 ProjectStore/IndexedDB、版本迁移、自动保存状态与项目文件导入导出。
- 复用 workspace reducer；持久化 registry、图表配置、局部修改、排除记录与 SourceRef，统一散落在 PageStateContext 的分析配置所有权。
- 提供草稿、命名项目、另存为模板、固定快照；保留当前会话撤销机制，重启后不承诺恢复旧撤销栈。
- 验收：刷新/重启保持数据和图表；存储配额不足显示失败且旧版本可打开；旧格式可迁移；多窗口冲突不覆盖；来源更新后提示版本不同。
- 依赖：T1。可独立于 T2–T4 推进，但本轮不启动并行执行。

### T6 数据范围和完整导出

- 将 ResultManifest 接入查询返回、工作区统计、数据范围提示；明确未知总数和截断状态。
- 增加工作区/全筛选两种导出；建立 ExportJob，服务器与桌面各有 dispatch 实现，进度 UI 复用任务状态协议。
- 改造当前同步 XLSX 路径；完整导出不再通过固定 limit 截断，资源超限时明确报错。
- 静态端实现相同范围语义和快照版本说明，使用自己的 DuckDB 读取路径。
- 验收：超过 200,000 行的验收集无漏行/重复；CSV/XLSX 数量一致；本地编辑仅影响工作区导出；导出中来源变化不会产生混版文件。
- 依赖：T1、T5；执行器终态保护复用 T3 的实现。

### T7 批次对比

- 以 AnalysisSpec 实现对比模板，复用字段元数据、查询过滤、Plotly 场景和选中联动。
- 首版固定为分布/差值/统一色标 wafer map，不新增任意统计建模引擎。
- 校验端口、单位、频段、结构与处理配置；不一致时展示差异并要求明确选择比较口径。
- 区分原始 pf 标记与自定义合格规则；每项指标使用自己的有效值样本数，空值不算零。
- 验收：相同数据自比较差值为零；缺失值、不同结构、不同频段均有明确处理；前后端统计在约定数值容差内一致。
- 依赖：T5、T6。

### T8 同步状态、设置与工作台

- capabilities 按实际模式提供操作能力；统一设置页承接现有 ServerSyncPanel 与发布配置。
- 复用 revision/receipt 显示同步状态，按目标分别显示处理成功、服务器确认、网页发布；冲突不静默刷新版本后覆盖远端修改。
- Electron 如需保存凭据使用主进程系统凭据保护接口，验证可用性；不可安全保存则保持会话输入。静态版不保存发布凭据；不得把 token 放入项目文件或浏览器持久存储。
- Dashboard 汇总最近项目、任务失败、质量问题与同步问题；按钮直接打开对应处理入口。
- 验收：断网、发布延迟、409 冲突显示真实状态；刷新后待处理问题仍可定位；静态版不展示无法执行的操作。
- 依赖：T2、T4、T5。落点：ServerSyncPanel/ServerAutoSync、Sidebar、Dashboard、同步服务。

### T9 报告与模型适用性说明

- AnalysisSpec + ResultManifest + Plotly 导出图生成自包含 HTML 报告；记录结论备注、单位、排除规则和数据版本。
- ONNX/模型产物元数据增加模型版本、训练范围、已有验证指标；没有验证数据时明确标为未知，不能生成虚假的置信区间。
- 验收：离线打开报告图表和来源说明完整，打印样式可用；报告统计与工作区一致；原始曲线未打包时明确说明。
- 依赖：T6、T7；模型说明可独立落地，不阻塞报告。

### T10 全流程验收与发布准备

- 三端分别执行：上传混合数据→查看验收单→重试失败→分析修改→保存并重启→对比→导出→同步→删除与恢复。
- 运行迁移、取消竞争、原生 SQLite 同步和 PostgreSQL 实际集成验证；纯 mock 测试不能替代这些验证。
- 记录大数据集的峰值内存、响应时间、自动保存耗时；以 T0 同一设备/夹具作比较，预算阈值在 T0 固定。
- 更新使用说明、兼容矩阵和回滚说明；数据库采用备份与前向修复，不依赖破坏性降级迁移。
- 依赖：所有目标发布工作包完成。部署/发布不属于本轮授权范围。
